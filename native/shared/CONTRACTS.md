# 原生架构与数据契约

两端分别实现原生界面与平台服务，共享业务规则和验收约束。本阶段不引入跨端运行时、KMP 或 C++，也不承诺 Swift 与 Kotlin 可以直接复用源代码。

## 已实现的依赖方向

`View -> LibraryModel/AppState -> MediaLibraryClient + ReviewStore`

- iOS：SwiftUI + @MainActor 状态模型；PhotoKit 查询在后台任务执行；SQLite 由 actor 串行管理。
- Android：Compose + AndroidViewModel；MediaStore、SQLite 在 Dispatchers.IO；界面状态在主线程修改。
- 服务协议/接口承接平台访问。UI 不直接执行照片删除或写入清理记录。
- 主题、小组数量是轻量偏好，分别使用 UserDefaults / SharedPreferences。
- 英文和简体中文使用系统资源；媒体标题来自平台。

## 稳定模型

- MediaAsset：完整平台 ID、媒体类型、创建日期、时长。Android 同时保留 content URI 和 MediaStore 大小；iOS 不伪造文件大小。
- MediaAlbum：ID、标题、数量、封面。保留 `all` 作为全库查询的应用内部标识。
- ReviewSession：媒体类型、相册、当前组最多 20 项、游标、标记 ID、删除请求意图。
- Reviewed：每个媒体类型的一组已确认 ID，包含保留项。跨相册复用，不能自动重置。

当前数据库格式分别由平台模型编码，没有跨平台二进制兼容承诺。后续旧版导入需要单独定义并校验转换格式。

## 删除和恢复边界

1. 点击或滑动只修改本组标记；写入成功后才推进到下一项。
2. 组末列出全部选择，由用户确认后发起一个系统批量删除请求。
3. 发起请求前保存删除意图；取消或失败保留会话。
4. 系统成功后，已确认 ID 和会话删除在同一 SQLite 事务提交。
5. 照片和视频使用不同的主键，互不覆盖。
6. 进程中断后的恢复路径尚待真机验收。已消失的目标不会再次触发物理删除。
7. iOS 删除进入系统最近删除；应用没有公开 API 可直接管理该系统相册。
8. 当前预览不包含 Android 应用回收站，不能将直接删除描述为可在应用内恢复。

## 后续迁移

- 清理队列：在本组基础上加入时间范围、冻结随机顺序与多组游标。
- 分析：单解码生成 dHash/清晰度/曝光，全局逐资产指标，与相册衍生结果分开。
- 大相册：已整理记录保持数据库行，缩略图与解码并发有界。
- 视频：同一时间一个播放器，邻居只显示缩略图，退后台停止播放。
- 旧数据：生产包标识和签名不变才能原地升级；旧 AsyncStorage 只读导入，校验成功才启用原生存储。未知/损坏格式不能覆盖为空。
- 真机验收完成前，继续使用独立的 `com.mediacleaner.app.nativepreview`。
